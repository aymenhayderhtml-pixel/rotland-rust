# R30.5-03: build settings, a faster play build, a faster gate

Owns: Cargo.toml (profiles only), .cargo/config.toml, tools/gate.sh, tools/build_speed.sh, tools/README_TOOLS.md, docs/BUILD_SPEED.md
Rules: `tasks/LEAD.md`. If `neon/in/R30.5-research.md` exists, read it first: it has online research on exactly this.

Current setup: stable Rust 1.99, mold linker, `target-cpu=native`, `[profile.dev] opt-level=1`, debug line-tables only, deps `opt-level=3`. `[profile.release]` uses `lto="thin"`, `codegen-units=1`, `panic=abort`. The owner plays the release build.

1. **`tools/build_speed.sh`:** the Phase 0 B measurements as one script (touch a file, time the build, print a table; release optional with `--release`). The lead uses it before and after.
2. **A faster play build:** add `[profile.play]` (inherits release; `codegen-units=16`, `lto=false` or `"thin"` without cu=1, `incremental=true`). The lead measures BOTH the build time AND the in-game FPS (perf_scenes) of `release` vs `play`. If `play` is within ~5% FPS, document `cargo build --profile play` as the owner's play build in `tools/README_TOOLS.md` (the binary is at `target/play/rotland`; check that path doesn't clash with the owner's copy, which also lives in `target/play/`, and if it does, pick another name such as `[profile.fastplay]`). Keep `release` for benchmarks.
3. **Dev/test speed:** try (and keep only what measures faster) `[profile.dev] incremental = true` (default, confirm), `codegen-units = 256` for workspace crates, `split-debuginfo` settings, `debug = 0` for tests, and `-Z` options only if they work on STABLE (they don't, so skip nightly-only ideas unless the research says a stable way exists). `cargo test --no-run` timing vs full.
4. **Faster gate:** `tools/gate.sh` now runs `clippy --all-targets` and then `cargo test`, which is two full type-checks. Measure first. Options: run clippy only on the crates the diff touched plus dependents; run `cargo test` with `--workspace` only when shared crates changed; skip `--all-targets` when no test files changed. **The gate must still catch every warning and test failure in changed code**, so when in doubt, keep it.
Every change gets a before/after number in `docs/BUILD_SPEED.md`. Changes that aren't faster get reverted.
